# 产品评审与下一轮验证

评审日期：2026-10-26。状态：**REVISE（收敛并验证）**。本文记录当前产品判断、证据边界和建议的工作顺序；不是收益报告，也不是新增功能已经实现的声明。

## 1. 结论与当前阶段

EvolveTrace 已具备邀请少量开发者试用的工程基础，尚不足以认定为成熟、值得广泛推广的开源产品。当前主要缺口是首次接入成本、普通用户对工作流的理解，以及相对于原始记录的实际审查收益。

下一轮建议集中验证一个问题：**不了解内部架构的开发者，能否独立接入，并比直接查看原始记录更快地完成一次正确的任务复核？**

| 维度 | 当前判断 | 仍需的证据 |
| --- | --- | --- |
| 场景合理性 | 长任务复核有合理使用场景 | 实际发生频率、问题严重度、现有替代方式是否已经足够 |
| 核心能力 | 采集、证据定位、确定性评估、人工复核和修正后比较已有入口 | 当前发布版本在真实宿主中的完整使用验证 |
| 首次接入 | 多步配置，仍有较高门槛 | 无作者协助的安装和首次收件结果 |
| 易理解程度 | Task、Run、Context、Receipt 等概念增加学习负担 | 新用户能否理解状态、判断证据并完成操作 |
| 行动闭环 | 人工复制修正提示，再执行和复核的路径已存在 | 用户是否完成全程，以及哪些步骤造成放弃 |
| 使用收益 | 未证明 | 定位时间、漏项、误报处理成本、自然复用情况 |

测试通过能说明所覆盖行为符合预期，不能证明用户节省时间、Token 或磁盘写入。产品收益也不能由单个 Run 的 accepted 状态推导。

## 2. 首要用户、触发时机与替代流程

首要用户是假设中的高频 Coding Agent 使用者：经常让 Codex 完成跨文件、长流程开发任务，并对代码接受和验证结果负责的个人开发者。暂不以组织级审计、管理者用量统计或硬件运维为首要市场。

首要触发时机：**Agent 宣称任务完成，开发者需要核对约定的验证依据。** 次要时机：Agent 长时间没有推进，需要定位反复失败的操作。

用户任务：当 Agent 提交结果时，我希望快速确认哪些验收条件有执行证据、哪些仍需补查，从而决定接受结果或要求补充验证。

不用 EvolveTrace 时的基线流程：

1. 回看需求和约束。
2. 翻阅 Codex 对话、终端输出和代码 diff。
3. 找到测试命令、退出结果及对应修改；必要时自己重新运行验证。
4. 判断是否接受，或给 Agent 补充说明。
5. 修正后再次核对。

推测的瓶颈是跨长记录查找、匹配验证依据和重复复核。瓶颈频率及耗时尚未量化。短任务、低风险修改或已有清晰 CI 结果的任务，直接看现有工具可能更便宜；应作为负例研究，而不是假定所有开发者都需要工作台。

## 4. 替代方案与可验证的差异

以下公开资料核对于 2026-10-26。产品供应说明存在替代方案，不能证明本项目已有需求或竞争优势。

| 替代方案 | 用户可以完成什么 | EvolveTrace 需要证明什么 |
| --- | --- | --- |
| 原始对话、终端、diff、测试和 CI | 直接核对修改与验证，额外部署成本低 | 长记录下定位更快、漏项更少，且收益超过配置与误报成本 |
| 将日志交给现有通用助手分析 | 按需获得解释和建议 | 可追溯的证据、未知状态及复核条件带来可观察收益 |
| Langfuse | Coding Agent 追踪、工具调用分析和失败会话重建 | 本地编码任务的接入和复核更直接，而不只是再提供时间线 |
| LangSmith | 线上评估、异常发现、人工复核及离线回归 | 无需搭建复杂评估工程，也能完成有依据的一次任务复核 |

资料：[Langfuse Coding Agent tracing](https://langfuse.com/resources/engineering/coding-agent-tracing)、[LangSmith evaluation types](https://docs.langchain.com/langsmith/evaluation-types)。

一句话产品假设：**为需要核对 Coding Agent 长任务结果的开发者，将约定条件、实际执行证据和缺口组织在一起，帮助他们更快决定接受或补充验证。**

“本地、轻量、面向编码任务的证据复核”是待验证方向。当前安装复杂度尚不足以支持已经很轻量的宣传。

## 5. 第一条产品闭环

目标路径：

> 一次性接入 → 明确本次验收条件 → 执行任务 → 核对条件与证据 → 人工决定 → 提供修正提示 → 新 Run 补充验证 → 按同一条件再次复核。

角色分工：

- 确定性软件负责采集、脱敏、关联、规则检查、证据展示和状态管理。
- 外部 Coding Agent 负责原本的代码任务及用户要求的修正；EvolveTrace 准备可复制提示，不自动接管执行。
- 人工负责定义验收条件、解释有争议的证据、确认标签及最终接受。
- 审计记忆只保留人工确认、有适用条件的记录；其被加载不证明它改变了 Agent 行为。

完成状态必须包含一个用户决策及其依据；需要修正时还应关联新 Run 的复核结果。生成报告、弹出提醒或显示更多统计本身不足以代表闭环完成。最终代码质量仍须结合实际测试、diff 和适用的独立验收。

异常路径要求：

- 未观测到必需验证：展示证据缺口，区分无法判定与已知失败，不能声称一定未执行。
- 服务、Hook 或绑定异常：给出具体故障层和下一步，不用历史记录代替本次收件成功。
- 用户未准备 Task：仍可查看会话证据；没有验收条件时不推断任务已合格。
- 正常重复操作或查询非零退出：允许核对、忽略、静音，避免一律判作失败。
- 修正未完成、证据仍缺失或用户中止：保留未解决状态，不能自动标为有效。

目标体验是在一个入口理解“哪里需要核对、依据是什么、处理后是否满足同一条件”。Task 创建目前仍依赖 CLI/API，完整表单和更简化的默认流程属于候选改进，不是现有能力。

## 6. 下一轮建议顺序与验收

### P0：交付已实现能力，验证首次接入

2026-10-26 执行结果与未关闭验收项见 [P0 交付验证记录](p0-delivery.md)。隔离探针、作者接入和独立使用者验证分别记录。

先核对并交付现有控制器、插件归档、版本说明和使用文档，再在当前宿主验证。自动启动只负责启动已经准备好的运行环境，不能把启用插件写成自动完成全部安装。

验收清单：

- [ ] 发布来源、插件归档、安装版本与使用说明一致，能明确复现对应版本。
- [ ] 新使用者按说明完成接入，记录耗时、失败步骤及额外帮助。
- [ ] 用一个无害任务确认本次 Session 与工具输入输出，分别检查服务、Hook、当前事件和绑定状态。
- [ ] 再次启动会话能按配置启动或复用服务；失败可诊断，不产生重复服务。
- [ ] 暂停与恢复行为可理解且符合实现；暂停采集仍保留 Context 和本地命令保护的边界清楚。

优先修复实测阻塞，再决定是否需要新安装器或原生开关，避免同时维护多套启动路径。

### P1：验证一次任务复核的理解和完成率

先观察用户使用现有线索、证据和反馈入口的过程，再做最小界面改进：默认突出待核对事项、证据与缺口、处理后结果；内部元数据按需展开。

验收清单：

- [ ] 用户能区分成功、已知失败、证据不足和单纯高频操作。
- [ ] 不经作者解释，完成一次证据定位和人工处理决定。
- [ ] 对需要补充验证的案例，能复制修正提示、在 Codex 执行并返回复核新 Run。
- [ ] 保留没有问题的案例，检查工具是否平白增加审查负担。

### P2：两周探索性试用与效果对照

在 P0 可用后，建议邀请 3–5 位经常使用 Coding Agent 的开发者。参与者尚待招募，排期从可用版本和参与者准备好后开始；样本仅用于发现明显问题，不代表市场需求已成立。

将首次安装观察、冻结案例效果对照、日常自然复用分开记录。效果对照使用同等资料、独立预期标签、交叉顺序和未见答案的案例；不能让同一人看到答案后再次评同一案例来宣称提速。

| 指标 | 用途与口径 |
| --- | --- |
| 接入完成率 | 无实时人工帮助完成接入的人数 / 所有开始尝试的人数；失败和放弃保留 |
| 首次价值时间 | 从开始安装到首次正确定位问题并作出决定；同时拆分安装与审查耗时 |
| 正确定位时间，主指标 | 按效果验证指南，从收到案例到正确指出预标注问题及依据 |
| 漏项与误报成本 | 按严重度保留未发现的问题、错误判断和误报处理时间 |
| 修正闭环完成情况 | 需要补充验证的案例中，完成新 Run 及同条件复核的数量和分母 |
| 自然复用 | 再次遇到适用任务的人中，主动使用的人数；没有再遇到场景单列 |
| 可靠性和开销 | 支持事件缺失、配对、任务绑定、Hook 延迟及额外排障时间 |

试验开始前冻结条件。建议的探索性继续标准为：正确定位时间中位数比原始记录减少 30%，不增加严重漏项，且配置、误报和额外操作没有抵消收益。**30% 是待确认的产品试验目标，不是行业标准或已测结果。** 报告全部案例、错误和超时；不能只比较成功案例，或仅凭小样本中位数认定有效。

停止或调整条件：

- 首次接入多数依赖作者救援：暂停新增分析能力，先解决交付。
- 用户最终仍依赖原始记录，工具未缩短定位或减少遗漏：检查提示、证据组织与目标场景。
- 误报处理或采集开销抵消收益：收窄规则、降低打扰或修复采集路径。
- 用户再次遇到同类任务仍不愿使用：调查原因；若现有替代方式已足够，暂停扩展该场景。
- 没有独立参与者：可先做披露限制的单人可用性验证，但外部收益和需求继续标为未知。

详细指标口径和记录字段复用 [effectiveness.md](effectiveness.md)，不另建一套相互冲突的指标。

## 7. 功能取舍和可行性

| 能力方向 | 下一轮建议 | 理由 |
| --- | --- | --- |
| 安装、状态诊断、已有控制器 | 优先交付和验证 | 是接触真实价值的前置条件 |
| 验证证据复核 | 首要验证 | 触发和完成状态明确，容易建立对照 |
| 重复失败提示 | 保留为次要场景 | 有排查价值，但重复不等于浪费，需要控制误报 |
| 跨项目上下文与审计记忆 | 保留，限制新增投入 | 支持复核和规则复用；独立记忆收益尚未证明 |
| 通用回归、更多评估器 | 按真实失败案例推动 | 避免用功能数量代替有效性 |
| 更多图表 | 有明确决策用途才增加 | 次数和图形不是结果指标 |
| 系统资源、磁盘健康 | 暂缓 | 需要新的采样、归因和诊断依据 |
| LLM Judge、RAG、云协作、通用 Agent 执行器 | 暂缓 | 增加依赖、成本与责任范围，尚非已确认瓶颈 |

以上是投资顺序，不是删除模块的结论。删除非简单封装前应说明职责、调用方、逻辑是否合理、替代与兼容成本；不能因产品价值未验证就断言代码错误。

主要可行性约束：参与者和独立标注者尚待落实；真实 Hook 覆盖依赖客户端版本；公开案例只能使用合成数据；私人轨迹、数据库及真实工作区上下文应保留本地。实验可先手工记录，不必先开发实验平台、自动遥测或收益看板。维护投入优先用于客户端兼容、状态诊断和证据准确性。
